## 2. AI 給了錯誤或不夠好的產出,以及怎麼修正

### 2.1 一開始沒查就選了 Node.js,你指定 Bun 後才改
- **問題**:AI 預設用 Node.js + Fastify,沒有先問或說明技術選擇。
- **誰發現**:使用者(「後端是用 Bun 嗎?」)。
- **修正**:改用 Bun + Hono。換之前先寫探針腳本確認所用函式庫在 Bun 上可運作,再動大量程式碼。
- **Bun 帶來的差異(都有處理並記錄)**:`Bun.serve` 預設 10 秒閒置就斷線,SSE 必須對該請求呼叫 `server.timeout(req, 0)`;`fetch` 預設同時最多 256 個對外請求,gateway 轉發 SSE 與 chat 呼叫 LLM 都會佔用,Dockerfile 設 `BUN_CONFIG_MAX_HTTP_REQUESTS=65535`;請求本文預設上限很大,改成 1MB。
- **教訓**:技術棧是需要使用者確認的決定,不該默默預設。

### 2.2 壓測:AI 猜錯兩次瓶頸,才用資料找到真因
- **現象**:3 個 chat replica 下出現 25% 的 503,且點數核對有誤差。
- **AI 的錯誤假設**:
  1. 以為是 DB 連線池太小。把 billing 連線池 10→40,隔離測試吞吐確實 +80%(2,500→4,500/s),但**真實流量下 503 沒改善**。
  2. 以為是往返次數太多。把熱路徑合併成單一 CTE 語句,**幾乎沒改善**。
- **真因**:壓測進行中查 `pg_stat_activity`,活動連線**全部**在等 `LWLock:WALWrite`,也就是每次 commit 等 WAL fsync。
- **驗證假設的過程也出錯**:暫時設 `synchronous_commit=off` 的實驗前兩次根本沒生效(第一次 `ALTER SYSTEM` 放在多語句裡被拒絕,第二次 shell 變數沒展開),卻「看起來有結果」。之後改成每次先 `SHOW` 確認設定,第三次才有效:2,500/2,500 成功。
- **決策**:**沒有**全域關閉 `synchronous_commit`(崩潰時會丟帳)。只對純簿記的狀態更新(`settle_pending→settled`,遺失可由冪等重送補回)用 `SET LOCAL`。
- **另一個錯誤**:最初用「1,500 人同一瞬間齊發」當壓測模型,不真實。改成固定到達率後才得到有意義的結論。1 個 replica 在 600 新對話/秒已飽和(TTFT p50 3.7 秒),3 個 replica 回到 125 ms、吞吐 197→537/s。
- **誠實紀錄**:同條件重複 4 次,p95 在 136–361 ms 之間波動,單次數字不可信;壓測與服務同機執行,**只能看瓶頸位置與擴充是否有效,不能當容量**。

### 2.3 「結果未知」造成點數凍結(壓測才暴露,功能測試測不到)
- **問題**:billing 過載時,chat 呼叫預扣逾時。AI 原本只在「確定預扣成功」才補償。但逾時不等於失敗,billing 可能已預扣、只是回應沒回來,於是點數被凍結。
- **更糟的一處**:補償用的 release 若也失敗,原程式把錯誤吞掉(`.catch(() => undefined)`)。
- **修正**:只有明確收到 4xx 才能確定沒預扣,其餘一律視為可能已預扣並補償;release 失敗時寫入 `pending_releases`,由背景 reaper 重試到成功。
- **誰發現**:AI(壓測後點數核對有誤差)。

### 2.4 只看小資料量的 EXPLAIN 會得到錯誤結論
- **問題**:幾百列資料時 `EXPLAIN` 顯示 `Seq Scan`,因為 planner 認為全掃更便宜,容易誤判索引沒生效。
- **修正**:灌到 200 萬列(983 MB)、再建一個 20 萬則的超長對話,才看到走 `Index Scan Backward`。keyset 分頁在翻到 19 萬則深時 0.14 ms,同需求用 `OFFSET` 為 3,905 ms。測完清掉測試資料。

### 2.5 寫文件、跑 Postman 時抓到的真 bug
- **(a) 登出後立刻重新登入,新 token 被拒約 5 秒**
  - 原因:gateway 的本機快取記住「這位使用者沒有有效 session」,首次登入時沒通知它清掉。
  - 發現:Newman 一開始 47 項失敗,逐步縮小到單一原因(先用最小案例排除「Postman 變數沒傳遞」的猜測,再用 curl 重現)。
  - 修正:登入成功一律發出通知。加了回歸測試,**並確認該測試在修補前會失敗**。
- **(b) 自己按登出,登入畫面卻寫「你的帳號已在其他裝置登入」**
  - 原因:伺服器登出時也會對自己的事件通道推 `session_replaced`(`reason: revoked`),客戶端一律當成被踢。
  - 修正:依 `reason` 區分;登出時先關閉事件通道。同樣加回歸測試並確認修補前會失敗。
- **(c) Postman 的空值選用參數**:`before_id=` 被後端判為 400。改成在 Postman 中預設停用。
- **(d) 文件中的數字寫錯**:AI 寫「完整執行約用掉 6 次註冊/登入限流」,實際量測是 5 次,已改。

### 2.6 接 Gemini:設計階段就避開的坑,以及驗證時抓到的 bug
- **思考(thinking)參數依模型世代而異**:2.5 系列用 `thinkingBudget`,3 系列用 `thinkingLevel`,送錯的一方會被悄悄忽略(照樣思考、照樣以輸出價收費)或被拒絕。因此做成環境變數 `GEMINI_THINKING`,不寫死。
- **模型名稱會過期**:查到的資料(多為第三方)顯示世代更替很快,預設名稱可能已下架或導向新版,所以放環境變數並在文件警告。
- **官方文件頁面抓不到內容**(被導向前端渲染的新網域):因此**格式是對照第三方整理與多個來源推得**,這是風險,見第 4 節。
- **AI 的 bug(備援驗證抓到)**:內容被安全機制擋下的錯誤也被計入斷路器。任何一位使用者連送幾則被擋的訊息,就能讓全站改走備援。修正:不是供應商故障的錯誤不計入,並加測試。
- **客戶端不一致**:即時串流會顯示「目前系統有問題」,但從歷史重新載入只有 `error_code`,畫面退回通用的「回覆中斷」。修正:客戶端以 `error_code` 對應文字。內容被擋時不再顯示無意義的重試按鈕。
- **驗證腳本自己的錯**:有幾個失敗是測試寫錯而非程式錯(計數被前一情境污染、指標標籤比對、重試時用錯 client_msg_id)。逐一釐清後修正測試,**沒有為了讓測試通過而放寬斷言**。其中「已不是最新的失敗訊息不能重試(409)」是後端刻意的保護,測試改成驗證這個行為。
- **文件過時**:ARCHITECTURE.md 原本寫「failover 是中期要做的事」,實作後已不正確,已更新並把真正的下一步(共享斷路器、全站預算)寫清楚。

### 2.7 輸入法選字時 Enter 誤送出(你回報的)
- **誰發現**:使用者。
- **原因**:AI 用 `CallbackShortcuts` 綁 Enter 送出,它不看輸入法是否正在組字,一律攔截。
- **修正**:改用 `Focus.onKeyEvent`,組字範圍有效時回傳 `ignored` 讓輸入法確認選字;Shift+Enter 仍換行。加 widget 測試,並暫時拿掉判斷式確認測試會失敗。
- **限制**:測試只能模擬「組字中」的狀態,**沒有用真實的注音/拼音輸入法操作過**。

### 2.8 其他較小的修正
- 直接讀 PDF 位元組是亂碼,改用 macOS PDFKit 抽取文字。
- Homebrew 安裝 Bun 失敗(要求 Command Line Tools),改直接下載官方 release,未動系統層級設定。
- macOS 沙盒預設沒有 `network.client`,App 連 `localhost` 會被擋,補上 entitlements。
- 剛搬完資料夾時,Postman / 驗證腳本的限流環境變數殘留在 shell 內,污染後續測試;之後每次改完都檢查並還原。
