## 1. 帳號與登入

- **註冊 / 登入,註冊贈送 200 點**
- **單一裝置登入:新裝置登入,舊裝置立刻失效並收到通知**
  - 需求要「單一裝置」。選「新登入踢舊」而不是「已登入就拒絕新登入」,因為使用者換手機、舊機遺失時,後者會把人鎖在外面。`sessions` 以 `user_id` 當主鍵,由資料庫保證最多一個有效登入。
- **踢人分三層檢查(gateway 記憶體 → Redis → auth 資料庫)**
  - 每個請求都要檢查,是熱路徑。99% 以上在記憶體就結束;資料庫才是真相來源。並發登入時,在持有資料列鎖的期間寫 Redis,避免 DB 與 Redis 最後的值不同。
- **Redis 寫入失敗時,登入直接失敗(fail-closed)**
  - 如果 DB 已換成新裝置、Redis 還是舊的,被踢的裝置會繼續通行。寧可拒絕登入,也不留下不一致。
- **即時通知舊裝置(`session_replaced` 事件)**
  - 使用者在舊裝置上要馬上知道「被別台登入」,而不是下次操作才發現 401。
- **刪除帳號:對話、點數明細、訂位需求全部刪除**
  - 題目要求。用 Outbox 發 `user.deleted` 事件,各服務自己清自己的資料,不跨資料庫操作;事件先寫進 DB 再送出,不會因為中途當機而漏刪。

## 2. 聊天

- **多位 AI 角色,每位使用者與每個角色只有一條連續對話**
  - 陪伴型產品的核心是關係延續,不是一次性的聊天串。
- **回覆逐字串流(SSE)**
  - 主流做法。
- **生成與連線脫鉤:使用者斷線或關掉 App,回覆仍在伺服器完成、存檔、結算**
  - 不能因為網路斷了就讓使用者「花了點數但沒回覆」。取消的只是「訂閱」,不是「生成」。回來時先給目前累積的全文,再接後續。
- **斷線續傳(`GET .../stream`)**
  - 生成可能在別台 instance 上,所以每 400 ms 把進度批次寫進 Redis Stream,任何一台都能接上。
- **冪等送出(`client_msg_id`)**
  - 手機網路不穩,App 會重試。重送同一則不能多出一則訊息、也不能重複扣點。
- **一個對話同時只能有一個回覆在生成(Redis 鎖)**
  - 避免使用者連點、雙裝置同時送出造成兩個回覆互搶。鎖只是「減少重複」的效率手段,最終正確性由資料庫的條件式更新保證,所以不需要 Redlock 那種重型方案。
- **訊息順序用 `seq`(每個對話嚴格遞增、無空洞),不用時間戳**
  - 兩台裝置、重送、時鐘偏差下時間戳會亂序或重複。客戶端用 `seq` 去重、排序,也用 `after_seq` 補回漏掉的訊息。
- **歷史紀錄用 keyset 分頁(`seq` 游標),往上滑任意深度成本不變**
  - 實測單一對話 20 萬則,翻到最深處 keyset 0.14 ms,`OFFSET` 3,905 ms。
- **AI 角色「記得」先前聊過的事:每次帶入最近 12 則 / 2500 字的歷史**
  - 每次請求都要重送並計費,是輸入成本的大頭,所以限制則數與字數。**目前不是長期記憶**,超過範圍的內容不會被記得;摘要記憶列在演進計畫。
- **失敗的回覆不扣點,且可用同一個 `client_msg_id` 重試,不留殘骸**
  - 使用者沒得到東西就不該付錢;重試沿用同一則訊息,歷史才不會出現一堆失敗的半成品。
- **chat instance 當機後由 reaper 補償**
  - 鎖 30 秒後過期,reaper 判定孤兒,從 Redis 撈回已產生的文字、標記失敗、釋放預扣。最多損失約 400 ms 的文字。

## 3. 點數

- **預扣 → 結算 / 釋放(兩階段扣點)**
  - 生成可能跑 8 秒才失敗,但不能因此卡住使用者,也不能等成功後才發現餘額不夠(期間餘額可能被別的請求花掉)。所以開始前先「預扣」,讓系統知道這筆點數暫時不能用;成功就結算,失敗就釋放回補。
- **不超扣:檢查與扣除是同一條條件式 SQL(`WHERE balance - held >= amount`)**
  - 靠資料庫的列鎖序列化,不靠應用層的鎖。再加 `CHECK (held <= balance)`、`CHECK (balance >= 0)` 當最後防線。實測 300 個並發搶 200 點,成功 200、被拒 100。
- **預扣、結算、釋放都是冪等的**
  - 補償任務會反覆重送,必須能安全重複呼叫。預扣用 `ref` 當主鍵,同一個 ref 並發 50 次只預扣 1 次。
- **「回覆完成」與「待結算」在同一個語句內提交(`billing_state` 狀態機)**
  - 不用分散式交易。把「還要補償什麼」寫進資料庫,reaper 每 15 秒掃一次;billing 暫時掛掉也不會漏帳。
- **預扣逾時一律當作「可能已預扣」,失敗時補償釋放**
  - 逾時不等於失敗。這是壓測時抓到的真 bug:billing 過載,預扣其實成功了但回應沒回來,導致點數被凍結。只有明確收到 4xx 才能確定沒預扣。
- **釋放失敗不吞掉,記進 `pending_releases` 由 reaper 重試;billing 另有 10 分鐘逾時清理兜底**
  - 補償本身也會失敗,不能靜默。
- **點數明細(帳本)使用者與客服都能查,每筆有 `ref_type`**
  - 題目要求。`ref_type` 區分聊天、訂位理解、訂位成功,`meta.booking_id` 可對回需求。
- **每日對帳:帳本總和 = 帳戶餘額總和**
  - 錢的問題要有第二道檢查,不一致就告警。

## 4. AI 模型(LLM)

- **供應商可切換:改 `LLM_PROVIDERS` 即可(mock / Gemini / Groq / OpenAI / Ollama)**
  - 模型更新很快,價格與品質常變。工廠依名稱建立,新增一家只要在註冊表加一行,不改業務程式。
- **缺金鑰或名稱打錯,服務啟動時就失敗**
  - 不要等到有人聊天才發現備援根本沒設定。
- **備援:主要供應商失敗且「還沒送出任何字」時,自動換下一家**
  - 涵蓋大多數故障(逾時、429、5xx、金鑰錯誤、空回覆),使用者無感。
- **已送出部分文字後才失敗,不換供應商,回報錯誤、不扣點**
  - 畫面上已經有字,中途換個模型重寫會讓內容突然被取代,更糟。
- **斷路器:連續失敗 3 次暫停該供應商 20 秒,之後只放一個探測請求**
  - 沒有它,主要供應商掛掉時每個使用者都要先等完逾時才換手,也會持續對壞掉的服務施壓。實測開路期間回覆 197 ms。
- **內容被安全機制擋下:不換供應商、不計入斷路器**
  - 不是故障;換一家去繞過過濾不妥;也避免一位使用者連送幾則就把整個供應商打到暫停。
- **全部不可用:回「目前系統有問題,請稍後再試」,不扣點**
  - 需求指定,且使用者沒得到服務就不收費。
- **成本控制:輸出 300 token、歷史 12 則 / 2500 字、使用者單則 500 字、Gemini 思考預設關閉**
  - 費用 = 輸入 × 單價 + 輸出 × 單價,兩端都要設上限。思考 token 以輸出價計費,對簡短聊天是純成本。
- **提早結束時主動關閉供應商串流**
  - 不取消的話,模型會繼續產生,輸出 token 照樣計費。
- **每則訊息記錄 `provider`、`model`、`input_tokens`、`output_tokens`,並有 Prometheus 指標**
  - 成本要先能「看見」,才能對帳單。

## 5. 快取與效能

- **Redis 分兩個實例:`redis-state`(不淘汰、AOF)與 `redis-cache`(LRU、不持久化)**
  - 放同一個實例的話,快取吃滿記憶體會觸發淘汰,把別人的登入狀態擠掉,使用者會莫名被登出。
- **最近 40 則訊息快取(write-through,Lua 以 `seq` 判斷附加 / 覆蓋 / 作廢)**
  - 同一份資料服務兩條最熱的讀取(組 LLM 上下文、開啟對話第一頁)。出現空洞就整個作廢重建,絕不憑空建出殘缺列表。
- **重建快取採「先安裝、再驗證」**
  - 重建期間可能有新訊息提交。安裝後對照 `next_seq`,不一致就作廢,避免快取漏訊息。
- **角色快取(cache-aside + 空值哨兵 + TTL 抖動 + single-flight)**
  - 分別防穿透、雪崩、擊穿。
- **所有快取路徑 fail-open(Redis 掛了退回讀 DB)**
  - 快取只是加速,不該變成單點。
- **熱路徑合併為單一 SQL 語句;純簿記更新用 `synchronous_commit=off`**
  - 壓測找到真瓶頸是 Postgres 的 WAL 寫入(138 個查詢全在等 `WALWrite`)。只對「遺失也安全」的簿記寫入放寬,涉及金額與內容的寫入維持同步,不降低耐久性。
- **chat / gateway 無狀態,可水平擴充**
  - 實測同樣 600 新對話/秒,1 台已飽和(TTFT p50 3.7 秒),3 台 125 ms。

## 6. AI 代辦:訂位

- **判斷是不是訂位需求(`POST /bookings/detect`,純規則)**
  - 一般聊天不該多花一次模型呼叫或點數。寧可漏判也不要誤判。
- **一句話建立需求:自動抽出日期、時間、人數、地區、料理**
  - 使用者只想說一句話。規則解析免費、快;設了金鑰則改用 LLM,失敗自動退回規則。
- **LLM 只負責「這一輪抓到哪些欄位」,不決定接下來問什麼、出什麼方案、送出什麼**
  - 這是整個設計最重要的一條線。模型最壞只是少抓一個欄位,不可能跳過檢查或改變送出的內容;輸出一律當不可信資料,重新驗證格式、範圍與日期。
- **找店:只列出搜尋得到訂位連結的店**
  - 列出無法代訂的店,使用者選了也沒用。
- **指定店名:搜尋該店的訂位連結;找得到店但沒連結,明說無法代訂、附電話、列同區替代店家**
  - 不讓使用者以為已經訂了,又不讓對話死在這裡。
- **缺什麼資料由店家的表單決定(姓名 / 電話 / email / 座位偏好…)**
  - 每家店要的資料不同。執行前先讀一次表單,「必填欄位 − 已提供的」就是要問的,不多問也不漏問。
- **方案有雜湊值,確認必須帶上使用者看到的那份的 `plan_hash`**
  - 擋住「手機看到方案 A,同時另一支裝置改成 B,然後在手機按確認」。不一致回 `409 PLAN_CHANGED` 並附最新方案。
- **確認的內容在資料庫層凍結(條件式 UPDATE + trigger)**
  - 「確認什麼就只能送出什麼」是硬規則。檢查與狀態改變是同一個原子操作;`confirmed_plan` 有值後 trigger 禁止修改,送出時只讀這一欄,連送到哪個網址都包含在方案裡。
- **在對話框打「確認」不會送出,必須走 `confirm` API**
  - LLM 可能把任何一句話理解成同意,有真實後果的動作不能靠語言理解。
- **方案 10 分鐘內有效,過期用資料庫時間判斷;草稿 24 小時沒動就作廢**
  - 餐廳位子會變動,方案不能放太久。判斷寫在確認的 SQL 裡,就算背景任務沒掃到,也不可能確認過期的方案。
- **隨時離開再回來:所有狀態都在 PostgreSQL**
  - 任何一台 instance 都能接手;`GET /bookings?status=active` 找回進行中的需求。
- **操作網頁的訂位同時最多 3 筆,第 4 筆回 `503 SERVER_BUSY`**
  - 需求指定。限制只管「送出表單」這段(唯讀的找店不受限);名額用 Redis 租約跨 replica 共用,當機後自動到期歸還;繁忙發生在確認那一刻,不改變任何狀態、不扣點。沒做排隊,因為要處理方案過期、使用者離開等情況,初期人少,回應繁忙更簡單可預期。
- **訂位管道是介面(`BookingChannel`):browser-agent(享樂地圖測試店家)**
  - 未來串平台 API 時,新增一個管道實作即可,不動其他部分。
- **通道把確認過的方案「機械式」對應到表單欄位,不讓 LLM 決定填什麼**
  - 讓送出的內容可以被證明等於確認的內容。實測 LLM 會按錯鍵、用過期的元素索引點錯,這些都會讓送出內容偏離確認內容。
- **真實實驗:享樂地圖測試店家,LLM 只選人數 / 日期 / 時段,訂位頁欄位由程式填寫並逐項比對,「確認訂位」只能由程式按下**
  - 同上。最終送出預設關閉(`BROWSER_AGENT_SUBMIT_ENABLED`),避免開發時意外建立真實訂位。
- **結果不明(送出了但沒收到回覆)時,網頁表單絕不自動重送,不扣點**
  - 網頁表單沒有冪等機制,重送可能重複訂位,比沒訂成更糟。
- **平台 API 用同一個冪等鍵(訂位 id)重送最多 3 次**
  - 平台保證不會重複,所以可以安全重試。實測平台第一次收單但回 503,重送後拿回同一個訂位編號,平台只有 1 筆。
- **write-ahead 記號(`exec_phase`):送出請求前先記 `submitting`**
  - 程序在送出途中當機,接手的 instance 要知道「到底送出了沒」。沒送 → 直接重做;送了且有冪等鍵 → 同鍵重送;送了但沒冪等鍵 → 標記 `unknown`,不重送。
- **訂位扣點:每輪 AI 理解 1 點、訂位成功 3 點,失敗 / 客滿 / 結果不明不扣**
  - 按鈕與表單不經 AI,不該扣;訂位比較貴因為代表「事情辦成了」;無法證明服務完成就不收費。
- **訂位結果與扣點結局在同一個 DB transaction 決定,reaper 每 5 秒重送通知 billing**
  - 不會出現「訂位成功但沒扣」或「失敗卻扣了」。
- **每次扣點嘗試用全新的 `ref`,目前有效的存在 `bookings.charge_ref`**
  - 驗證時抓到的真 bug。固定 ref 時,第一次因點數不足被拒、補點後再確認,會出現訂位成功卻沒收到錢、預扣卡住。
- **冪等與併發保護:同一則訊息只處理一次、同一筆需求並發操作只有 1 個成功(其餘 `409 TURN_IN_PROGRESS`)**
  - 手機重試與雙擊很常見,不能因此多扣或重複處理。
- **聯絡資料只存在該筆需求,不跨需求預填**
  - 電話 / email 是個資。預填是好功能,但要先決定保留期限與使用者同意。

## 7. 後台

- **查使用者、點數明細、對話內容、訂位紀錄;補點;管理角色**
  - 客服要能查問題、處理客訴。
- **只綁 `127.0.0.1`,沒有權限控管**
  - 依需求未做。**正式環境必須先加 SSO、RBAC、操作稽核**,因為它能看對話與改點數。

## 8. 客戶端(Flutter)

- **聊天畫面:逐字顯示、歷史往上滑、斷線續傳、被踢出時的通知**
  - 後端的行為要在畫面上看得到。
- **點數明細對話框**
  - 對應「使用者能查明細」的需求。
- **訂位畫面、訂位紀錄**
  - API 的 `pending` 欄位直接告訴客戶端該顯示什麼(選店 / 補資料 / 確認方案),畫面不需要自己判斷流程。
- **SSE 解析器處理「封包切在中文字 UTF-8 位元組中間」**
  - 串流中文時這是實際會發生的錯誤,有專門的測試。

## 9. 維運與部署

- **一鍵啟動:`docker compose up -d --build`(PostgreSQL、2 個 Redis、各服務)**
  - 降低上手成本,不需要任何 API key。
- **只有 gateway(8080)與後台(127.0.0.1:8090)對外,`/internal/*` 永不轉發**
  - 縮小攻擊面,服務間呼叫不暴露給外部。
- **每個服務一個資料庫,禁止跨庫查詢,只走 API 或事件**
  - 邊界才是真的。本機共用一個 Postgres 實例省資源,但連線字串已分開,拆機器不用改程式。
- **滾動更新不砍斷進行中的串流(draining 模式,最多等 20 秒)**
  - 同時約 1,800 條長連線,直接砍會讓大量使用者的回覆中斷。逾時才強制中止,並釋放預扣。
- **migration 以 advisory lock 序列化,且只做向後相容的變更**
  - 多 replica 同時啟動安全;舊版程式可以跑在新結構上,rollback 才可行。
- **`/metrics`、`/healthz`、`/readyz`,結構化 JSON 日誌,`x-request-id` 貫穿各服務**
  - 出問題時要能追到是哪個服務、哪個請求。只記 5xx 與慢請求,避免高併發下 access log 的成本。
- **端到端測試:聊天冒煙 36 項、LLM 備援 44 項(用假的 LLM 伺服器模擬故障)**
  - 可靠性靠異常情境的驗證,不靠推論。
